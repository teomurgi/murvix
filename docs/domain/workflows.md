## WF-01 Register, edit and remove a project

**Actor/trigger:** desktop user or management caller adds an existing folder, changes shared metadata or removes registration. **Preconditions:** selected server/Home known; valid directory/metadata and operation capacity. **Rules:** [BR-01](business-rules.md#br-01-project-identity-and-home), [BR-02](business-rules.md#br-02-workspace-roots-and-availability).

1. Desktop constructs an independent descriptor/ID, queues a `ProjectIntent` and updates its projection. It saves before replaying; edit/save failure restores prior memory. CLI management instead resolves and submits its request directly.
2. Server checks intent identity and receipt, applies the mutation through catalog validation/persistence, and returns an outcome. A repeated matching operation gets its prior outcome; a mismatched token is refused.
3. Clients refetch after catalog invalidation. Desktop rejects changed/duplicate server identity, merges only a complete catalog and overlays still-pending edits. Shared name/color updates do not replace its private tabs/order. Acknowledgements must complete queued intents in order.
4. Removal marks project and direct children deleting, then ends/discards their sessions and removes descriptors. Files remain. Offline desktop removal can remain queued; ordinary deletion is not worktree-file removal.
5. An externally missing worktree can be pruned only under the server's no-membership/definitively-missing conditions; the desktop also avoids pruning one with tabs or conflicting pending intents.

**Outcomes/failures:** rejected metadata/folder, full client queue, identity mismatch, persistence error, or resumable cleanup. An error after catalog rename does not prove nothing changed. **Collaborators/messages:** client projection ↔ server catalog; `Changed { topic: Catalog, revision }` prompts refetch, not durable edit replay.

## WF-02 Share, close, detach and restore terminals

**Actor/trigger:** desktop/TUI/CLI caller creates or attaches a terminal, closes a view, ends a program, disconnects or returns. **Preconditions:** valid project and negotiated server protocol; an attachable live session for live attachment. **Rules:** [BR-04](business-rules.md#br-04-session-creation-and-operation-identity), [BR-05](business-rules.md#br-05-close-detach-and-session-references), [BR-06](business-rules.md#br-06-output-retention-history-and-input-acknowledgment).

1. Create reserves a receipt/membership before starting shell/PTY. A matching retry does not create a second process. Spawn/publication failure follows the unavailable/stop paths, not a fake live fallback.
2. Attach establishes a channel and initial screen/recent history/metadata. First attachment can set size; additional attachments do not automatically replace an existing attached size. Explicit resize changes the shared terminal for everyone. Multiple clients can provide input.
3. Visible views consume frames and acknowledge credit. Hidden layout references may preserve participation without active screen traffic. Search/history requests page retained output; stale cursors cause refresh/error rather than unrelated rows.
4. Ordinary close removes a view, persists pending cancellation/close and synchronizes references; server decides whether another participant preserves the session. Detach/disconnect removes presentation/stream participation without ending it. Explicit end/discard/project deletion is global rather than a private-view close.
5. Natural/explicit termination drains trailing output, attempts final archive and sends `SessionEnded`; panes referencing it close. End keeps saved content; discard removes it. Catalog exit persistence may lag/retry independently.
6. Reopen matches `(project, session)` against the selected server: attach matching live sessions, close missing references, create only unbound available-project panes. Server restart recovers output records, not programs; retention later removes eligible ended/unavailable records.

**Failure branches:** PTY input timeout may follow a write; archive failure can lose output; an unreadable existing archive can list as ended but fail read. Disconnected saved layouts do not preserve a terminal against another connected client's explicit close decision. End All Sessions and Quit affects local terminals and cannot undo process termination if later UI save fails.

## WF-03 Arrange views or apply a project layout

**Actor/trigger:** desktop user opens/splits/moves/zooms/closes views, groups tabs, or explicitly chooses Apply Layout. TUI user changes its independent terminal layout. **Preconditions:** available project/valid local view; trusted parsed file for application. **Rules:** [BR-07](business-rules.md#br-07-local-view-consistency-and-pin-protection), [BR-08](business-rules.md#br-08-explicit-project-layout-application).

Ordinary edits preserve local identities while changing layout/focus, remove empty tabs/groups and use neighboring focus. Desktop mutation wrappers restore prior memory on edit/save failure. TUI changes lock/reread current shared TUI state, clone, validate, persist and then allow further effects; storage recovery failure blocks further session actions. This sharing is among TUI instances, not desktop/TUI layout synchronization.

For a project file: list candidate files → load/parse with resource limits → show explicit destructive confirmation → recheck directory and tab/pane identity snapshot → replace every project tab, including pins → persist new views/startup commands → cancel old pending creations and request close of now-unreferenced sessions → create/attach new terminals when server is ready. Failed parse or changed confirmation snapshot leaves the old layout rather than knowingly applying stale consent. Offline connection can defer new terminal creation.

**Outcomes/messages:** local view state plus later server operations; extension view-change notifications may follow, but no cross-process atomic layout-applied event is established. Local startup-command consumption is not proof of exactly-once shell execution after arbitrary failure.

## WF-04 Observe and acknowledge agent activity

**Actor/trigger:** a supported coding tool runs in a terminal; desktop/TUI/CLI reads activity; user focuses/acknowledges attention. **Preconditions:** live terminal evidence; eligible connected desktop for native notification claiming. **Rule:** [BR-17](business-rules.md#br-17-agent-attention-and-notification-claims).

Session process-group inspection identifies provider; bounded screen/title/progress heuristics update working/blocked/idle. Stable evidence after a working cycle may produce Completed; blocked/provider changes may produce Attention. Per-session attention replaces prior unread attention. Server sends revision invalidation; desktop refetches, filters to participating background terminals, requests claims and asks OS notification service only for claimed still-eligible IDs. Focus attempts acknowledgment; success removes the alert across clients and clears local notification, failure preserves refresh/error state. Claim does not acknowledge or certify display.

**Separate resume branch:** local visible agent-history panel scans supported provider transcript files under bounded budgets, matches exact project directory and deduplicates provider+ID. A selected still-existing validated transcript creates a tab/startup resume command; save failure restores view state. Provider tool, not Murvix, decides whether resume succeeds. Seven providers support history/resume; recognition of twelve does not imply twelve resume implementations. Remote project history scanning is not established in this path.

## WF-05 Work on Git and worktrees

**Actor/trigger:** desktop user, CLI or authorized extension inspects/mutates repository, creates/removes checkout, commits or opens/manages PR. **Preconditions:** selected server project resolves to an actual repository; guarded operations need current expected snapshots/approved hooks; AI generation additionally needs an installed local provider. **Rules:** [BR-03](business-rules.md#br-03-worktree-creation-and-removal), [BR-09](business-rules.md#br-09-git-review-and-destructive-operations).

- **Inspect/change:** server validates project/repository and obtains common-repository read/write lock, then translates Git output into summary, branches, status, changes, log, diff and review preview. Stage/unstage/discard/checkout/branch/tag/cherry-pick/revert use their distinct operation semantics. External repository changes remain possible.
- **Create/register worktree:** lock/replay operation receipt → reserve identities/path → validate parent/destination/membership → persist receipt → run Git/create/PR checkout → optional approved setup → register child. Setup failure returns the registered project plus failure, not rollback.
- **Remove checkout:** capture/approve inspection and optional teardown → revalidate identity/status → stop associated sessions/processes → teardown → Git removal → catalog cleanup. Changed approval/directory, unsafe process stop or teardown failure blocks file removal, but earlier termination cannot be undone. Register-only project deletion is a different workflow.
- **AI commit/PR:** user confirms action/provider/choices against branch/head → prepare review/context (possibly staging all) → run selected AI CLI locally → parse/validate generated metadata → apply expected-head/tree commit → optional push or branch/push/PR creation. Current source has no second generated-draft review step. Generation/apply failure can leave staging/commit/branch/push already done.
- **PR management:** server `gh` adapter translates PR info/list/diff/create/merge/close/update/checkout. Checkout builds verified remote/tracking branch and PR-number config. Update checks open/non-fork/head/local cleanliness; failed merge attempts abort, failed push can leave a local merge. PR creation/readback can fail after push/creation.

**Outcomes/messages:** operation-specific result/partial-failure explanation; coalesced `GitChanged` may refresh clients. No global Git/catalog/GitHub/AI transaction is established. **Not established:** end-to-end remote AI generation usability, because inspected provider execution uses desktop-local project directory while Git requests use the project's server.

## WF-06 Compose and deliver terminal input

**Actor/trigger:** user edits project draft, attaches file/image, dictates or submits selection/full draft to active/visible terminals. **Preconditions:** editable draft store, valid attachments, live target(s), no active recording/submission. **Rules:** [BR-11](business-rules.md#br-11-draft-and-submission-preservation), [BR-13](business-rules.md#br-13-file-upload-and-exec-constraints).

1. Edit text/files; debounce ordinary publication. Pasted image preparation checks draft revision, stores image/placeholder and publishes; malformed data or ambiguous publication preserves originals/blocks overwrite rather than silently clearing.
2. Prepare selected or full content, expand recognized image tokens, validate files and capture/deduplicate target server/session identities. Nonblank selection excludes ordinary file attachments.
3. Remote targets upload files/images and quote returned remote paths. Local clipboard strategy leases clipboard, sends paste-image input with a pause, then text; unsupported image clipboard falls back to inline paths. Project/generation/channel checks reject stale destinations.
4. Await input-write completion per target. Clear only original draft revision after successful delivery; preserve intervening edits. Partial failure preserves draft and reports already completed targets; it cannot unsend earlier bytes/uploads.

**Voice branches:** composer inserts final transcript at current selection; standalone dictation captures terminal target, drops stale results and optionally sends Return. Recorder transitions Starting → Recording/Paused → Transcribing → Finished or Failed. Empty transcript/error stays visible rather than pretending success. macOS requires on-device speech and permissions; Linux requires local capture/transcriber/models. No live speech backend was exercised.

## WF-07 Connect a remote server or pair a device

**Actor/trigger:** user configures SSH endpoint or enables pairing; a compatible client connects. **Preconditions:** endpoint credentials/host trust or locally approved TLS offer and compatible protocol. **Rule:** [BR-10](business-rules.md#br-10-connection-authority).

**SSH branch:** select configured endpoint → launch SSH/askpass as applicable → remote `murvix stdio` bridges its local server socket → protocol negotiation → catalog identity validation → restore per-server views. Connection loss preserves cached UI. Recoverable remote failures retry after two seconds with exponential backoff capped at one minute; required password/host-key/authentication intervention and an explicitly stopped server prevent blind retry. Missing remote installation may offer a pinned release installer or development archive route; live asset/install success is not established. Forgetting a remote removes that endpoint's local projection, not remote server projects. Folder availability checks apply only to the latest ready connection/check; unknown failures are not automatically proof of a missing folder. [crates/murvix-app/src/model/reconnect.rs:42–114](../../crates/murvix-app/src/model/reconnect.rs#L42-L114), [crates/murvix-app/src/model/remote_files.rs:375–445](../../crates/murvix-app/src/model/remote_files.rs#L375-L445).

**TLS branch:** local user enables listener → create five-minute one-use offer with advertised hosts/fingerprint → client pins server certificate, negotiates protocol, pairs with offer → server persists hashed credential/device state → later credential authentication. Invalid/expired/reused offer fails. Owner disconnect cancels offer; disabling/revoking disconnects device connections. Device permissions differ from SSH account authority. `mobile pair` wording assumes a compatible client; no phone application is provided here.

## WF-08 Extend or automate the desktop workspace

**Actor/trigger:** user installs/loads/enables/updates extension, invokes contribution, or caller automates browser. **Preconditions:** valid package/native backend and declared permissions/consent where applicable; desktop app/profile for browser socket. **Rules:** [BR-12](business-rules.md#br-12-extension-authority), [BR-14](business-rules.md#br-14-browser-scope-and-profiles).

**Extension branch:** download verified package into staging or remember canonical unpacked folder → validate manifest/resources → install/refresh → enable by separately stored name → register contributions/start eligible background/scripts/pages. Calls establish registered owner/document/liveness, authorize, preflight/ask sensitive consent, dispatch and resolve only for still-live scope. Denial/timeout/expired scope/disconnected server produces error, not an authorized fallback. Disable/remove retires runtime, prompts/jobs/surfaces and grants as appropriate; unpacked removal leaves source files, separate data/settings can remain. Update checks identity/version, asks open views where implemented, disables during swap, attempts rollback and restores enablement only without added permissions.

**Browser branch:** manual page actions, local JSON socket requests or permitted extension calls converge on app-owned browser panes. Open resolves project/profile, persists pane and rolls memory back on save failure; hidden pages may be created for automation. Navigation/extraction/DOM actions/eval/waits/screenshots/storage/cookies use the native page. Missing elements generally return false/null; waits can time out; native callback operations have different timing limits. Profile deletion refuses default and retargets affected panes. A remote project does not move the browser engine to the remote machine.

**Language branch:** enabled resource-only provider validates bundle/catalog placeholders; selection reloads global language/menus/windows. Missing/disabled/failed provider falls back to English; runtime script support is not required to read catalogs.

## WF-09 Personalize, back up and restore a profile

**Actor/trigger:** user changes settings/theme/shortcuts, opens Quick Terminal, exports/imports/restores configuration or imports older settings/projects. **Preconditions:** supported capability/editable profile; valid archive/effective configuration for restore. **Rules:** [BR-15](business-rules.md#br-15-configuration-restore-and-exclusions), [BR-18](business-rules.md#br-18-personalization-locale-and-platform-availability).

Ordinary preferences target app TOML sections, native terminal configuration, server settings or access settings according to authority; there is no single global preferences transaction. Slider preview is temporary until save. Theme selection combines built-in and overriding user themes; Omarchy reads external palette/generation and writes only the profile theme. Custom commands create titled terminal tabs/startup shell text. Quick Terminal toggles a local Home terminal: hide preserves it, close uses termination/reference policy; Linux global shortcuts require X11 rather than Wayland.

**Export:** flush/snapshot model → collect allowed configuration roots and sanitized local layouts → write temporary archive → publish export. Collection is not a transaction with every concurrent writer. **Restore:** choose/validate → confirm stages next-launch import → startup first recovers an interrupted journal → revalidate/remap/materialize → snapshot originals in Backups → persist journal → sequentially replace roots/install allowed migrated additions → clear pending/journal. Failure attempts compensation; failed recovery prevents loading known-partial state. Server mobile settings use a separate callback and retain pending file until success; paired secrets are not restored.

**Legacy branches:** supported 1.x import reports unsupported options and merges existing content; installed-project merge can be immediate. Automatic installed-profile migration is conditional (Home-only/no prior markers and not an explicitly selected `MUXY_DIR` profile), not universal. Installed extension migration copies missing packages as an exception to normal backup exclusions.

## WF-10 Install and replace executables

**Actor/trigger:** user installs app/CLI/server or accepts update; maintainer runs release automation. **Preconditions:** supported package/platform, complete matching helpers, approved compatible update and actual distribution assets. **Rule:** [BR-16](business-rules.md#br-16-safe-executable-replacement).

Installed release app checks/downloads validated feed/artifact and persists schedule. User chooses protocol-compatible preservation, waiting until idle, or explicit terminal-ending update. Flush/save precedes preparation; fresh identity/build checks and stop-if-idle avoid a race with session creation. Preserve leaves compatible old server alive until idle; explicit shutdown loses processes before replacement and cannot be undone by bundle rollback.

macOS stages verified signed bundle/helpers, retains prior bundle and attempts replacement/restart rollback. Linux user install stages complete version directory then switches current pointer, retaining previous version and leased helpers; helper launch/early-exit observation is not a semantic workspace health test. Uninstall is constrained to managed installation/links, not profile/session data. Standalone CLI installer switches matching CLI/server pair and protects unrelated commands unless explicit replace; desktop CLI installation similarly verifies bundled helper identity and existing-link ownership. Remote installation is a separate SSH/internet operation, not automatic propagation of a local app update.

**Ancillary release branch:** current workflows authorize maintainer initiation, compute stable SemVer release PR, verify exact merged version/tag, build/sign/package target matrix and publish complete draft assets/checksums/update feed behind configured gates. Repository guidance conflicts with this flow on manual stamping/tagging; see [Q-06](open-questions.md#q-06-release-guidance-and-packaging-disagree). Static files establish intended automation, not that live publishing/approvals/signing are configured or succeed.

## WF-11 Operate files or bounded commands without a terminal view

**Actor/trigger:** management caller or authorized extension sends file/Git JSON or exec request; terminal/composer uploads attachments. **Preconditions:** selected project/session, allowed connection authority and permission. **Rule:** [BR-13](business-rules.md#br-13-file-upload-and-exec-constraints).

File requests resolve from authoritative server project root, validate traversal/type/selection, then read or mutate; watches coalesce changes and may request rescan. Collision-sensitive rename differs from mkdir/move suffix selection. Batch mutation can fail after earlier items completed. Delete goes to OS Trash; Git discard has different permanent-delete semantics. Remote file opening fetches bytes, saves a local temporary mode-0444 copy and opens it; failure reports an error rather than opening the remote path as a local original. File upload refuses directories and files over 100 MiB; a multi-file failure can leave earlier uploads. Returned paths are pasted only if the captured pane attachment/connection generation still matches, so a changed target can leave uploaded files without pasted paths. [crates/murvix-app/src/model/remote_files.rs:48–103,294–313,449–484,557–585](../../crates/murvix-app/src/model/remote_files.rs#L449-L484).

Exec resolves project start context and optional cwd/environment, starts argv or shell command, drains bounded output/stdin, and reports completion plus timeout/cancel/truncation flags. CLI exposes argv-only form; extensions can choose shell/async cancellation. Cancel/disconnect/timeout terminates process group, rather than retaining a reconnectable terminal. One-shot CLI rejects persistent Git/file watch actions.

## Events and messages

This is the canonical event account. **Not established:** a persisted domain-event bus, replayable business history, exactly-once delivery or a global order across connections/files/processes.

| Representation | Producer → consumer and significance | Observed delivery limits/evidence |
| --- | --- | --- |
| `SessionEnded { session, reason }` | Session termination → connected clients; domain-significant occurrence represented as an integration message. Clients retire channels and close affected views. | Final-save attempts precede report; catalog persistence can retry independently. **Observed extension event vocabulary:** `pane.created`, `pane.closed`, `pane.focused`; `tab.created`, `tab.closed`, `tab.updated`, `tab.focused`; `project.switched`, `worktree.switched`, `projects.changed`, `worktree.headChanged`; `agent.status`, `file.changed`, `notification.posted`; panel/popover/modal opened/closed; targeted `command.<id>`; owner-local `extension.*` messaging. Pane events concern terminals, `pane.focused` is within-project/tab split focus and carries no pane ID, and `worktree.headChanged` compares known branch name rather than every new commit. Command/runtime-shortcut and owner-local events have declaration exceptions. See [crates/murvix-app/src/model/extensions/events.rs:200–448,587–672](../../crates/murvix-app/src/model/extensions/events.rs#L587-L672), [crates/murvix-app/src/model/extensions/calls.rs:248–303](../../crates/murvix-app/src/model/extensions/calls.rs#L248-L303).

**Observed technical callbacks, not domain events:** native page load/message/navigation/asset callbacks, script API calls/errors, Promise replies, modal query/result callbacks, before-close acknowledgements and native screenshot/cookie completions coordinate UI/RPC. A logged error is diagnostic evidence, not a newly modeled business occurrence.
