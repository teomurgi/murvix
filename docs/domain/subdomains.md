## Why this is not one context per crate

**Observed:** the workspace dependency policy spans nine crates, while the same project descriptor is shared by server operations and client state; the app-core `Project` adds client-local tabs and status to that descriptor. See [Cargo.toml:1–30](../../Cargo.toml#L1-L30), [crates/murvix-protocol/src/project.rs:87–116](../../crates/murvix-protocol/src/project.rs#L87-L116), and [crates/murvix-app-core/src/project.rs:70–98](../../crates/murvix-app-core/src/project.rs#L70-L98).

**Inferred:** organization cuts across persistent work, repository work, and local presentation. The technical package tree therefore cannot establish strategic subdomains or bounded contexts by itself. In particular, a worktree is both a Git checkout and a registered child project, and a browser tab belongs to local presentation rather than server terminal state.

## What remains unestablished

No inspected artifact establishes domain-expert consensus, strategic investment priorities, buy/build decisions for whole subdomains, or organizational DDD relationships. Confirmation would require product-owner and maintainer validation, not larger code-size measurements. The open questions record these limitations without proposing a redesign.
